# Передача и синхронизация мира

Протокол 5403 сохраняет RNG-правила и ID команд Guard 5401/5402. Существующие Guard-checkpoint с историей совместимы; перед сменой протокола сохраняется отдельная копия. Оба игрока должны обновить программу перед общей сессией. Переход обязателен для исправленной отправки контрольных данных и защиты от потери сравнений.

## Изменения

Для Radmin и локального IPv4 создаются отдельные UDP-менеджеры на одном порту. Upstream `LiteNetManager.Create` объединяет адреса по порту и сохраняет только последний IPv4: прежняя передача обоих адресов одним вызовом оставляла только loopback. Хост подключался, а удалённый игрок получал ошибку подключения без записи о новом соединении. Теперь каждый адрес привязывается отдельно и выводится как `UDP listening`; ошибка любой привязки отменяет запуск всех менеджеров. Регрессионная проверка устанавливает UDP-соединения по двум IPv4 на одном порту.

Крупные снимки идут по TCP на том же IP Radmin и порту 30502. Одноразовый 256-битный токен выдаётся только после входа по UDP, привязан к адресу участника и ограничен по времени. Клиент проверяет длину и SHA256 всего тела; затем сервер подтверждает выбор TCP по упорядоченному управляющему каналу. Лишь после подтверждения клиент применяет мир. При отказе TCP или таймауте используется UDP. Запоздалое подтверждение не приводит к повторному применению мира.

Команды, поступившие за время TCP-загрузки, сохраняются на серверном цикле и идут после подтверждения снимка. При откате на UDP сервер заново захватывает текущие данные, включающие эти команды. Симуляция, RNG-проверки и gzip-проверка снимка сохраняются.

UDP учитывает фактический MTU LiteNetLib. Раньше блок приложения занимал 1024 байта, а стандартный MTU библиотеки давал 1020 байт полезного надёжного сообщения: получалось повторное дробление. Теперь блок помещается целиком; после успешного MTU discovery допускается до 1400 байт. Принудительно поднимать MTU адаптера не нужно. Частота игрового тика и несинхронная обработка игровых событий не менялись.

Для быстрого пути на хосте должен быть доступен **TCP 30502** серверного EXE на сети Radmin. **UDP 30502** остаётся каналом команд и резервом загрузки. При блокировке TCP передача откатится на UDP.

## Измерения

Release-сборка; полный MP-сейв пользователя; передаваемое тело 2 320 964 байта. UDP измерялся через локальный прокси с искусственной задержкой в обе стороны. Это стенд без ограничения полосы, а не сеть друга. TCP измерялся отдельно на loopback без такого прокси. Проверка содержимого каждого принятого тела прошла.

| RTT прокси | Старые UDP-блоки 1024 | Блоки 1020 | Блоки 1400 при доступном MTU |
|---|---:|---:|---:|
| 0 мс | 2,340 с | 1,210 с | 0,854 с |
| 50 мс | 6,942 с | 3,360 с | 2,442 с |
| 100 мс | 11,145 с | 5,556 с | 4,086 с |

Для профиля 1400 стенд задавал MTU 1404 обоим концам — это модель найденного MTU, а не настройка Radmin. TCP на loopback: 38,3 / 24,8 / 25,7 мс для того же тела с проверкой хеша. Эти числа нельзя переносить на интернет/VPN. Предел зависит от исходящего канала хоста, RTT, потерь и маршрута Radmin.

UpdateTime 15 → 5 мс заметного выигрыша при задержке не дал, поэтому изменение не включено. Импорт/упаковка исходного ZIP в первом замере занимал около 271 мс; прежняя UDP-передача была значительно дольше.

## Диагностика

В Player.log пишутся `SYNC wait-host`, `SYNC transfer`, `decode`, `SYNC world-load`, `SYNC replay`. Ранее «Loaded game in 0ms» измеряла постановку загрузки в очередь; теперь отмечается и фактическое завершение. На TCP прогресс считается по прочитанным байтам, деление на нулевой интервал исключено.

Быстрая доставка файла не устраняет стоимость построения карты и проигрывания команд. Периодические точки Guard сокращают историю, но эти фазы нужно измерить в настоящей сессии. Замера между двумя физическими ПК через Radmin пока нет.
